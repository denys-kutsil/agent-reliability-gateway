# Проєкт простими словами

Цей файл для тебе. Тут без складних слів: що ми будуємо, що вже зроблено і навіщо.

## 1. Одним абзацом

AI-агент (наприклад, Claude) вміє викликати зовнішні сервіси: календар, пошту, CRM. Ці сервіси іноді
ламаються. Коли вони ламаються, агент повторює запит, і виходять **дублі**: лист надіслано двічі,
зустріч створено двічі.

Ми будуємо **шлюз**. Це охоронець між агентом і сервісами. Він не дає зробити одну дію двічі і
повторює запити розумно. А ще ми **міряємо цифрами**, наскільки шлюз допомагає.

## 2. Сам експеримент

Беремо одну й ту саму задачу: «створити зустріч → надіслати лист → створити контакт». Проганяємо її
кілька разів, щоразу з іншим захистом:

| Конфіг | Що увімкнено                      |
| ------ | --------------------------------- |
| A      | Нічого. Агент просто повторює     |
| B      | Шлюз тільки з повторами           |
| C      | Повтори і захист від дублів       |
| D      | Усе                               |
| E      | D і підказки з документації (RAG) |

Сервіси ламаються **однаково** в усіх прогонах. Тоді різниця в цифрах залежить тільки від захисту.

Дивимось на: скільки дублів, скільки задач успішні, скільки часу, скільки запитів на задачу.

## 3. Що вже зроблено

Кожен крок: **що**, **навіщо**, **що це дає далі**.

### ARG-01. Основа проєкту (monorepo, CI)

- **Що:** папка з кількома пакетами, тести, перевірка стилю, автоматична перевірка на GitHub.
- **Навіщо:** щоб код не псувався непомітно. Після кожної зміни GitHub сам запускає `lint`,
  `typecheck` і `test`.
- **Далі:** усі наступні задачі живуть в цій структурі. Якщо щось зламається, CI покаже червоне.

### ARG-55. Локальний режим

- **Що:** команди `pnpm run setup` і `pnpm run doctor`. Вони піднімають базу даних у Docker.
- **Навіщо:** щоб усе працювало на твоєму комп'ютері без AWS і без ключів.
- **Далі:** ідемпотентність і ліміти шлюзу зберігатимуть дані в DynamoDB. Локально це DynamoDB Local
  з цього кроку.

### ARG-02. AWS-акаунт і порожній CDK

- **Що:** акаунт AWS, безпечний вхід, бюджет «нуль доларів», порожній стек.
- **Навіщо:** щоб можна було одною командою розгорнути проєкт в хмарі і одною видалити.
- **Далі:** усе, що ми додаємо в AWS (Lambda, черги, таблиці), описується кодом у цьому стеку.

### ARG-03. Три фальшиві сервіси (mock-провайдери)

- **Що:** Calendar, Email і CRM. Три маленькі HTTP-сервери. Вони навмисно різні: Calendar це
  звичайний JSON, Email приймає форму і має свій захист від дублів, CRM відповідає кодом 200 навіть
  на помилку.
- **Навіщо:** справжні сервіси не можна ламати за бажанням. А наші можна.
- **Далі:** саме по них «їздить» агент в експерименті. Шлюз потім має працювати з усіма трьома, не
  знаючи їхніх особливостей.
- **Де працює:** локально (`pnpm mock`) і в AWS як Lambda.

### ARG-04. Навмисні збої (fault injection)

- **Що:** сервіси тепер вміють ламатися за планом. Три профілі: `low` (5% запитів ламаються), `high`
  (25%), `outage` (2 хвилини повністю лежить). Чотири види поломки:
  - 429: «зачекай», дія не виконана;
  - 503: «не працюю», дія не виконана;
  - таймаут: тиша, дія не виконана;
  - **втрачена відповідь**: дія **виконана**, а відповідь загубилась.
- **Навіщо:** щоб був реальний «поганий день» для API, який можна відтворити.
- **Seed (числовий ключ).** Збій залежить від номера запиту. Той самий номер дає той самий збій.
  Тому A, B, C, D бачать однакові поломки, і порівняння чесне.
- **Головне.** «Втрачена відповідь» це єдиний режим, який дає дублі. Ти зробив запит, дію виконано,
  але ти про це не знаєш. Повторюєш, і виходить два.
- **Далі:** усі прогони експерименту йдуть по цих збоях. Шлюз перевіряється саме на них.
- **Побічно:** я розклав файли пакета по папках (`providers`, `faults`, `state`, `transport`,
  `app`), щоб було зрозуміліше.

### ARG-05. Агент без захисту і перший вимір (config A)

- **Що:** `packages/agent`. Агент за сценарієм (не AI) виконує задачу з трьох кроків. Якщо помилка,
  одразу повторює, до 3 спроб. Runner проганяє 200 задач і рахує результат.
- **Навіщо:** щоб побачити, **скільки шкоди без шлюзу**. Інакше не буде з чим порівнювати.
- **Дублі рахуються зі сховища сервісу**, а не зі слів агента. Агент не знає, що створив дубль.
- **Результат (200 задач):**

| Профіль | Успішні | Задачі з дублями | Дублів усього |
| ------- | ------- | ---------------- | ------------- |
| low     | 100%    | 3.5%             | 7             |
| high    | 96.5%   | 17%              | 38            |

- **Далі:** це **відправна точка**. Коли шлюз буде готовий, ми проженемо ті самі задачі і
  порівняємо. Мета: дублів стало 0, а успішність не впала.

## 4. Як це все пов'язано

```
агент ──► mock-сервіс (ламається за seed) ──► сховище записів
                                                    │
runner ◄── рахує дублі, дивлячись у сховище ◄───────┘
```

Зараз агент іде напряму до сервісу. Потім між ними з'явиться шлюз:

```
зараз:  агент ─────────────► сервіс
потім:  агент ──► ШЛЮЗ ──► сервіс
```

Агент, сервіси, збої і runner залишаються тими самими. Змінюється тільки один блок.

## 5. Що далі

1. **Stage 0.** Панель керування (NestJS): користувачі, ролі, ключі агентів. Бекенд, без фронтенду.
2. **Stage 2.** Сам шлюз, три механізми:
   - **Ідемпотентність:** друга така сама дія не виконується, а повертається перша відповідь.
   - **Повтори:** розумні, з паузами, тільки там, де це безпечно.
   - **Звірка:** після обриву шлюз сам перевіряє, чи дія таки виконана, замість сліпого повтору.
3. Прогони **B і C**. Порівняємо їх з A: це перші цифри користі шлюзу.
4. Пізніше: LLM-агент, документація для агента (RAG), circuit breaker, бюджети, аудит.
5. Наприкінці: графіки, документ про архітектуру, пост і резюме.

## 6. Слова, які зустрічаються

| Слово           | Просто                                                         |
| --------------- | -------------------------------------------------------------- |
| Mock            | Фальшивий сервіс, який поводиться як справжній                 |
| Fault injection | Навмисне ламання, щоб перевірити захист                        |
| Seed            | Число, з якого «випадковість» виходить однаковою щоразу        |
| Дубль           | Зайвий запис, створений повтором запиту                        |
| Ідемпотентність | Повтор тієї самої дії не створює нічого нового                 |
| Retry           | Повторити запит після помилки                                  |
| Reconcile       | Звірити: чи дія таки виконана, перш ніж повторювати            |
| p95             | Час, у який вкладаються 95% запитів. Показує «повільний хвіст» |
| Конфіг A–E      | Варіант експерименту з різним захистом                         |
| JSONL           | Файл, де кожен рядок це один запис з результатом               |
